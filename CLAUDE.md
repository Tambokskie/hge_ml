# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HGE Database — Honor Graduate Eligibility Latin Honor Database. A plain-PHP (no framework) web app where schools' PDF lists of Latin Honor graduates are uploaded, OCR/text-extracted into structured records, reviewed/corrected by a human, saved, and later searched to verify whether an applicant holds a Latin Honor for a given school/year. The original PDF is always retrievable as the source of truth.

Design spec and phase plans (useful for "why" context, not just "what"): `docs/superpowers/specs/` and `docs/superpowers/plans/`.

Terminology used consistently in code/UI: **HGE**, **Application** (this system), **PDF** (an uploaded school list), **Latin Honor** (`CUM LAUDE` / `MAGNA CUM LAUDE` / `SUMMA CUM LAUDE`), **Applicant** (a graduate holding a Latin Honor — never the uploader).

## Commands

```
composer install                 # PHP deps (smalot/pdfparser, tesseract_ocr, phpunit)
npm install                      # Tailwind
npm run build:css                # compile assets/css/input.css -> assets/css/app.css (minified)

vendor/bin/phpunit                                    # run full test suite
vendor/bin/phpunit tests/includes/FunctionsTest.php   # single file
vendor/bin/phpunit --filter testMethodName            # single test
```

Tests need a real MySQL/MariaDB server reachable at `127.0.0.1` as `root` with no password (`tests/TestDb.php` creates/tears down a separate `hge_masterlist_test2` database from `database/schema.sql` — it does not touch `hge_masterlist`; the name has a `2` because the original `hge_masterlist_test` picked up permanent InnoDB dictionary corruption on one dev machine — see `TestDb::DB_NAME`'s comment — and was abandoned rather than repaired in place). There is no PHP lint/static-analysis command configured. `tests/config/DatabaseTest.php` connects to `hge_masterlist_test2` directly without creating it, so running it in isolation on a machine that has never run the full suite fails with "unknown database" — run the full suite (or any other `TestDb`-using test class) at least once first.

CI (`.github/workflows/tests.yml`) runs the same `vendor/bin/phpunit` against a MySQL 8.0 service container on PHP 8.2, with Ghostscript/Tesseract installed via `apt-get` (paths resolved into `GHOSTSCRIPT_PATH`/`TESSERACT_PATH` env vars) and `npm run build:css` run first — mirror that setup when debugging a CI-only failure.

The app itself is served by XAMPP/Apache at `http://localhost/hge_masterlist/` — there is no dev server to start.

## Architecture

**No framework, no router, no autoloader for app code.** Every page under `admin/*.php` and every endpoint under `api/*.php` is a standalone script that begins by manually `require_once`-ing exactly the `config/` and `includes/*.php` files it needs (order matters: `config/database.php`, then `includes/functions.php`, then `includes/auth.php`, then feature-specific includes). Only `vendor/` (Composer deps and the `Tests\` namespace) is autoloaded. When adding a new admin page or API endpoint, follow the require pattern of a sibling file rather than inventing a bootstrap file.

**`includes/*.php` are function libraries, not classes** (except the extractors). Each file groups plain functions around one concern: `auth.php` (session, CSRF, login, role checks), `functions.php` (view helpers: `e()`/`e_upper()` escaping, `asset_url()` cache-busting via `filemtime`, pagination, flash messages, dashboard stats), `uploads.php`, `schools.php`, `graduates.php`, `users.php`, `activity.php`, `extraction_review.php`, `pdf_files.php`. All DB access takes an explicit `PDO $pdo` parameter — nothing reaches for a global connection inside these functions (call `get_pdo()` once in the page/endpoint and pass it down).

**Auth/session model**: `require_login()` / `require_role('administrator')` (see `includes/auth.php`) gate every admin page and API endpoint. Roles are `administrator` and `user`; `user_has_role()` treats `administrator` as satisfying any role check. Every state-changing API endpoint verifies `csrf_verify($_POST['csrf_token'])` before doing anything else — copy this check when adding a new endpoint. `attempt_login()` deliberately runs `password_verify()` against a fixed dummy bcrypt hash when the user doesn't exist or is disabled, to avoid a timing side-channel; don't "simplify" that away. For especially sensitive actions (e.g. `api/backup_database.php`), a valid session + CSRF token isn't enough: the endpoint re-collects username/password from the request body and re-runs `attempt_login()` fresh ("step-up" re-authentication) before proceeding — follow that pattern for any new endpoint that exports/destroys data at that level of sensitivity. Idle-session timeout is enforced server-side in `require_login()` against `SESSION_IDLE_TIMEOUT` (`config/database.php`, default 14400s/4h, `getenv()`-overridable) and mirrored client-side: `includes/footer.php` emits the same timeout value to `assets/js/idle_timeout.js`, which pings `api/keep_alive.php` on user activity to reset `$_SESSION['last_activity']` before it expires, and otherwise redirects to `login.php?timeout=1`.

**Extraction pipeline** (the core domain logic). PDF is the primary input path:
1. `admin/upload.php` → `api/upload_pdf.php` → `handle_upload_request()` in `includes/uploads.php`: validates the PDF, finds/creates the school, detects duplicate school+school_year uploads (`confirm_duplicate` is required to add another one — it never overwrites the earlier upload, it is stored as the next `upload_number`), builds a collision-safe stored filename (the first upload keeps `..._2025_1.pdf`; the 2nd, 3rd… get `..._2025_dup01.pdf`, `..._dup02` — `build_stored_filename()`; `upload_dup_tag()` reads the tag back from the stored name for the DUP01 badge on `admin/duplicates.php`; `database/rename_duplicate_upload_files.php` is the one-off that renamed older uploads — only those with an earlier sibling, so a lone #2 keeps its name), copies the file into `storage/pdfs/` (denied to direct web access via its `.htaccess`), and inserts a `latin_honor_uploads` row.
**Image uploads (JPG/JPEG/PNG)**: `admin/upload.php` also accepts a single JPG/JPEG/PNG photo or scan of a list. `validate_pdf_file_content()` accepts `application/pdf`, `image/jpeg` and `image/png` by detected content and returns the stored `extension` (`pdf`/`jpg`/`png`) — never taken from the uploaded name; `handle_upload_request()` passes it to `build_stored_filename()`. An image is ONE page: `api/extract_pdf.php` (`$isImageUpload = is_image_filename(...)`) skips Ghostscript page counting/slicing, sends the stored file itself to `GeminiExtractor` (which picks `image/jpeg`/`image/png`/`application/pdf` via `mimeTypeForPath()` from the extension; the image is never unlinked as a "chunk"), skips `GenericExtractor` (no text layer) and, when the admin opts into OCR, `OcrExtractor` runs Tesseract on the image directly. A multi-photo list = one upload per image (the later ones become `_dupNN`). `api/serve_pdf.php` serves the right `Content-Type` via `mime_type_for_filename()`; the PDF drawer iframe shows an image as-is, with FILE FORMAT from `pdfDetails.fileFormat`. Extend `is_image_filename()`/`mime_type_for_filename()` rather than hardcoding an extension.

2. `api/extract_pdf.php` runs a fallback **chain**, each stage only tried when the previous one fails: **`GeminiExtractor`** (the primary path) sends the PDF's raw bytes directly to the Gemini API (`config/gemini.php`: `GEMINI_API_KEY`/`GEMINI_API_KEY_2`/`GEMINI_API_KEY_3`/`GEMINI_API_KEY_4`/`GEMINI_MODEL` via `getenv()`, no hardcoded default for the keys — an unset key makes it fail immediately and fall through, so a fresh clone works unmodified) and asks it to read the document and return structured JSON rows directly, understanding layout (wrapped cells, borderless columns, narrative certification letters) without a bespoke per-layout handler. It tries each configured key in turn, up to four (a 429 skips straight to the next key — quota exhausted, no point waiting; a 503 or transport failure gets 2 short-backoff retries on the *same* key first), and `extract_pdf.php` gives it one bounded extra whole-extractor retry when the failure wasn't quota/connectivity-related. Documents are sent in 2-page chunks (`AI_EXTRACTION_CHUNK_PAGE_SIZE`; a 3-page chunk of a dense list measured ~90s and 124 output rows). Timing is deliberately layered under Apache's 300s `Timeout`: one request to Google may take up to `GeminiExtractor::REQUEST_TIMEOUT_SECONDS` (180s), `api/extract_pdf.php` raises PHP's limit to 280s and gives the extractor a shared time budget (`setDeadline()`, 255s) so no request or retry starts with under `MIN_ATTEMPT_SECONDS` left; running out of time (curl timeout after connecting, or the budget) is reported as `timed_out` — distinct from `unreachable` (never connected) and from quota — moves on to the next key without repeating on the same one, skips the extra whole-extractor retry, and shows "THE AI TOOK TOO LONG TO ANSWER" instead of letting PHP die mid-request (see `GeminiExtractorTimeoutTest`). **The API keys have a provider each** (`includes/app_settings.php`: five slots, `resolve_ai_key_slots()`, each connected to `gemini` or `claude` through the dropdown in Settings → AI Extraction Settings / `api/update_gemini_keys.php`; slots 1-4 keep their original `gemini_api_key*` settings and default to Gemini, slot 5 (`ai_api_key_5`, env `AI_EXTRACTION_KEY_5`/`AI_EXTRACTION_PROVIDER_5`, `config/claude.php`) defaults to Claude). `extract_pdf.php` walks the slots through `prioritize_claude_slots()` (Claude keys first, Gemini behind them, slot order kept within each) and `group_ai_slots_into_segments()` — neighbouring keys of one provider form one segment handled by that provider's extractor (which rotates through them) — and the first segment that returns rows wins. **`ClaudeExtractor`** (`extractors/ClaudeExtractor.php`, model `CLAUDE_MODEL`, default `claude-opus-5-5`) calls the Anthropic Messages API over plain curl (no SDK: this deployment has no working Composer): the PDF slice/image goes in as a `document`/`image` block with the same prompt as Gemini's, the answer is forced into a JSON schema via `output_config.format`, effort is `low`, and a `refusal`/`max_tokens` stop yields no rows; a 429, an empty credit balance or a rejected key (401/403) moves to the next key, a 529 or transport failure is retried on the same key, and its result carries `quota`/`unreachable`/`timed_out` like the Gemini one. `admin/upload.php`'s usage gauge still counts only the Gemini keys (Claude has no free-tier cap to estimate). If AI still fails, **`GenericExtractor`** (text-layer via `smalot/pdfparser`, fast/free, no OCR) is tried next; only if that also yields zero rows does `extract_pdf.php` return `ocr_confirm_required` and wait for the admin to explicitly opt into **`OcrExtractor`** (Ghostscript rasterizes pages to PNG, then `thiagoalessio/tesseract_ocr` OCRs each page — paths configurable via `GHOSTSCRIPT_PATH`/`TESSERACT_PATH` env vars) via `use_ocr=1`, since OCR is the slowest and least accurate option and shouldn't run silently. `GeminiExtractor::isQuotaExhausted()`/`getUsageStats()` back a usage-gauge/notice on `admin/upload.php`, backed by a small JSON cache file in `storage/cache/` (not the DB — disposable, resets daily) rather than a real "remaining quota" figure (the free tier exposes none). `includes/functions.php:ai_availability_tier()` turns that single estimated-usage percent into the indicator's three states by how much is still assumed *available* (100 minus the used percent): 100%-60% available is green ("AVAILABLE"), below 60% down to 40% is yellow ("MODERATE USAGE"), below 40% is red ("LOW AVAILABILITY") — one deterministic formula, no separate signal or override; a real extraction failure shows up in it automatically (it lowers the same underlying count, and a genuine quota failure pins `isQuotaExhausted()`'s flag, hence the available percent, at 0 for the rest of the day) rather than needing its own rule. All extractors implement `ExtractorInterface::extract()`; `GenericExtractor`/`OcrExtractor` additionally share row-parsing logic via the `ParsesHonorRows` trait (AI output needs no such parsing — Gemini returns the fields directly).
3. `ParsesHonorRows::parseRows()` (used by `GenericExtractor`/`OcrExtractor` only) is line-oriented text parsing (no ML/NLP): it locates the honor phrase (`CUM LAUDE` family) on a line, then works backwards/forwards from that position to pull name, course, GWA, and date, handling name-first, "course-first" (anchored on `BACHELOR`), and "honor-first" (honor between name and course, or leading the line with the row's name/number OCR'd onto a separate fragment) layouts. A line with no honor phrase is tried as a **ditto row** (`parseDittoLine()`) — many Philippine school lists repeat `"- do -"` in the Honor Received/Date columns instead of retyping the same value; since real OCR renders that mark wildly inconsistently ("do", "odo", or unrecognizable noise), it's detected by anchoring on the course keyword instead of the ditto text itself, then `resolveDittoMarks()` backfills honor/date from the nearest earlier row in a second pass over the whole document. Separately, when a table cell's course text wraps onto 2-3 lines, OCR sometimes splits the honor phrase itself across the line break — `mergeSplitHonorLines()` (run before per-line parsing) joins such a line with the next one whenever that completes a recognizable honor phrase within the next line's first ~20 characters. `mergeOrphanedHonorFragmentLines()` similarly re-attaches an honor tier name OCR'd onto its own line, separated from the row's actual content by a genuinely blank line. `matchHonor()`'s CUM↔LAUDE gap is intentionally bounded slop (not `\s*`) to tolerate what typically sits in that gap once merged. Whichever extractor produced them, rows are staged into `$_SESSION['extraction_review']` (see `includes/extraction_review.php`), never written to `latin_honor_graduates` directly.
4. `admin/review.php` lets a human edit staged rows (`set_staged_row()`), remove one (`remove_staged_row()`) or several at once (`remove_staged_rows()`, multi-select bulk-delete UI), and mass-set a graduation date across every staged row (`mass_update_staged_graduation_date()`, for lists whose PDF never had a date column). **UPLOAD EXCEL** (`api/import_review_rows.php`, `includes/review_import.php`) bulk-adds graduates from a spreadsheet — headers `Name of Honor Graduate`, `Course`, `Honors Received`, `Date of Graduation` (aliases accepted, header row found in the first 10 rows; `.xlsx`/`.xls`/`.csv` via `bulk_hge_read_upload()`) — as the quick fix when the AI/OCR misread a list: `parse_review_import_rows()` (pure) builds rows with `source = manual`, `append_staged_rows()` appends them to `$_SESSION['extraction_review']` (nothing is saved until SAVE RECORDS), a row with a missing name or an unrecognized honor is skipped and reported, and a missing/unreadable date keeps the row undated with the year from the upload's school year; the file itself is not stored. A header-only template is downloadable from `api/download_review_import_template.php` (`build_review_import_template_xlsx()`), linked from a DOWNLOAD TEMPLATE button beside UPLOAD EXCEL and from the upload modal. Every removal path — staged (`api/delete_graduate.php`/`api/delete_graduates.php`) and already-saved (`api/delete_saved_graduate.php`) — requires a free-text `reason` first (`validate_removal_reason()` in `includes/functions.php`: non-empty, letters/numbers only, rejects placeholders like "N/A" or "-"), folded into the `record_removed` activity-log entry rather than stored on the row itself. A review in progress can also be persisted server-side rather than only living in `$_SESSION`: `api/save_draft.php` → `save_extraction_draft()` writes the staged rows into `extraction_review_drafts` (one row per `upload_id`) and sets `extraction_status` to `draft`, so it survives past the session and can be resumed later. `api/save_records.php` → `save_staged_records()` validates every row (`validate_staged_row()`) and, in one transaction, reconciles them against the DB by `id`: rows carrying an `id` (seeded by `get_graduates_for_upload()` when **reopening an already-`reviewed` upload for editing**, e.g. from `admin/school_records.php`'s "Edit saved records" link) are UPDATEd in place, rows without one are INSERTed as new, and any existing saved row whose `id` no longer appears in the submitted set is DELETEd — so the same function handles a first-time save and a later correction to already-saved records alike, only then setting `extraction_status` to `reviewed`. Clicking SAVE RECORDS first calls `api/check_save_duplicates.php`: `find_staged_duplicate_groups()` (`includes/duplicates.php`) groups staged rows that are duplicates by **name** (`duplicate_group_key()`) of another staged row, or of a record already saved ANYWHERE — any school, course, year or honor — under a different upload (`find_saved_duplicates_by_name()` in `includes/graduates.php`, applied copies first; it also feeds the review table's duplicate badge, whose tooltip names the school and any application); if any exist, a modal lists them with each saved copy's school and the admin removes selected staged rows (through `api/delete_graduates.php`, reason required, then the page reloads), saves anyway, or cancels back to the review — nothing is saved by the check itself, and `save_records.php` does not enforce it (it is a prompt, not a gate).

**Re-extracting an upload whose records are already saved** (`reviewed`, e.g. an earlier OCR reading was unclear): `admin/view_upload.php` offers RE-EXTRACT WITH AI / RE-EXTRACT VIA TEXT/OCR (RE-READ TEMPLATE for an `.xlsx` upload) for administrators, and `api/extract_pdf.php` only accepts a `reviewed` upload when the request carries `reextract=1` (the confirmation, which shows how many records are kept and replaced). Nothing is written to `latin_honor_graduates` until SAVE RECORDS. Every extraction path runs its rows through `merge_reextracted_rows()` (`includes/extraction_review.php`), which protects the **tagged** records — saved graduates with a row in `graduate_applications`: they are carried into the review as `locked` rows (same id and data, `applied_on` set; first batch only), a new row with the same name (`duplicate_group_key()`) is dropped because the applied record prevails, and a new row matching an untagged saved record takes over its id so `save_staged_records()` UPDATEs it in place; saved records the new extraction does not reproduce are removed on save into the Recycle Bin (`review_edit`). Locked rows cannot be edited, removed (`staged_row_is_locked()`, `STAGED_ROW_LOCKED_MESSAGE`) or have their date changed by MASS UPDATE DATE, are shown on `admin/review.php` with an APPLIED tag and a lock, and `save_staged_records()` neither validates, updates nor deletes them. While a draft exists `records_extracted` keeps the real count of saved records (`count_saved_graduates()`), so such an upload cannot be removed. Covered by `ReextractionTest`.

**Changing an upload's campus** (`admin/view_upload.php` → CHANGE CAMPUS quick action, administrators only; `api/change_upload_campus.php` → `change_upload_campus()` in `includes/uploads.php`): moves a list filed under the wrong campus to another campus of the SAME school — `get_other_campuses_for_upload()` offers only the other ACTIVE `schools` rows with the same `school_name` (case/space-insensitive), so a single-campus school gets a "no other campus" message pointing to School Management. In one transaction it updates `latin_honor_uploads.school_id` and the `school_id` of the upload's `latin_honor_graduates` and `graduate_recycle_bin` rows; the extracted data and every `graduate_applications` row are untouched, but the stored file is renamed to carry the new campus (`rename_upload_file_to_match_school()` → `build_stored_filename()`, e.g. `..._UNIVERSITY_2026_1.pdf` → `..._UNIVERSITY_SAN_JORGE_2026_1.pdf`; it updates `stored_filename`/`file_path`, keeps `original_filename`, refuses to overwrite a different file already holding the new name, undoes the rename if the transaction fails, and does nothing when the file is not on disk). The upload keeps its `upload_number` unless the target campus already has that number for the same school year (the unique key is `school_id`+`school_year`+`upload_number`), then it takes the next free one. Logged as `record_updated`. Covered by `ChangeUploadCampusTest`.

When changing text-based parsing behavior, extend `ParsesHonorRows` (shared by `GenericExtractor`/`OcrExtractor`) rather than duplicating logic in one extractor, and check `tests/extractors/GenericExtractorTest.php` / `OcrExtractorTest.php` plus the PDF/OCR-output fixtures in `tests/fixtures/` (including `course-first-sample.pdf`, `course-first-scanned.pdf`, `ditto-sample-ocr-output.txt` — verbatim real Tesseract output of a ditto-mark honor list, `wrapped-course-honor-split-ocr-output.txt` — verbatim real Tesseract output of a wrapped-course honor list, `bped-bsab-course-ocr-output.txt` — verbatim real Tesseract output covering the `BPED`/`BSAB` course abbreviations, `vsu-honor-first-ocr-output.txt` — a layout where the honor sits between name and course, and `sti-ormoc-honor-leading-ocr-output.txt` — a layout where the honor tier is OCR'd onto its own orphaned line ahead of the row it belongs to, all used as-is rather than re-OCR'd on every test run) for the layouts already covered. `tests/extractors/GeminiExtractorTest.php` covers `GeminiExtractor` against a stubbed API base URL (`buildGeminiRequestPayload()`/`parseGeminiResponseRows()` are pure and unit-tested directly; transport failures are exercised by pointing `$apiBaseUrl` at an unreachable local address, no real network dependency). The hardcoded `COURSE_KEYWORDS` list (only relevant to the text-parsing fallback path) is not exhaustive — when a GenericExtractor/OcrExtractor document has a row that silently disappears, it's almost always a missing course abbreviation there. Rather than editing code for a one-off addition, an administrator can add it live via **Settings → OCR Course Keywords** (`admin/ocr_courses.php`): `includes/ocr_keywords.php` stores admin-added keywords (always uppercased, restricted to `A-Z0-9.- ` to keep every row a plausible abbreviation) in the `ocr_course_keywords` table, `api/extract_pdf.php` loads them and passes them into `new GenericExtractor($keywords)` / `new OcrExtractor($keywords)`, and `ParsesHonorRows::courseKeywordPattern()` compiles them (`preg_quote()`'d — never trusted as a regex fragment) alongside the hardcoded list into the same pattern used everywhere `COURSE_KEYWORD_PATTERN` used to be referenced directly.

**Upload From Template (Excel), an alternate input path**: alongside PDF, `admin/upload.php`'s "EXCEL TEMPLATE" tab lets an admin skip extraction entirely by filling in a structured `.xlsx` template instead. **Download**: `api/download_template.php` (`?school_id=`) generates it on the fly via `build_latin_honor_template_xlsx()` in `includes/xlsx_writer.php`, pre-filling the exact `school_name`/`campus` from the DB so a re-upload always matches. **Upload**: `api/upload_template.php` → `handle_template_upload_request()` in `includes/template_upload.php` does in one request what the PDF path spreads across two (`upload_pdf.php` + `extract_pdf.php`), since there's no extraction step: read the file (`xlsx_read_first_sheet()` in `includes/xlsx_reader.php`), validate its header block + column layout (`parse_latin_honor_template()` — pure/DB-independent, unit-tested in `tests/includes/TemplateParsingTest.php` without a DB), resolve the school via `find_school_by_exact_name_campus()` (unlike the PDF form, **never** auto-creates a school — an unrecognized school is a hard `school_not_found` error telling the admin to add it in School Management first), then the usual duplicate-check/store/`create_upload_record()`/`start_extraction_review()` sequence — it lands in the same `$_SESSION['extraction_review']` staging session as the PDF path, so review/save downstream is shared. The `.xlsx` itself is kept as the source-of-truth file in `storage/templates/` (sibling to `storage/pdfs/`, same `.htaccess` deny), and `TemplateExtractor` (in `extractors/`, implements `ExtractorInterface` like the others, covered by `tests/extractors/TemplateExtractorTest.php`) re-runs the same reader/parser pair for RE-EXTRACT RECORDS. Since a `latin_honor_uploads` row's stored file can now be either format, anything that assumed "PDF" checks `pathinfo($upload['stored_filename'], PATHINFO_EXTENSION)` instead (`admin/view_upload.php`'s FILE FORMAT/quick actions, `admin/review.php`'s preview button, `api/serve_pdf.php`'s `Content-Type`, `api/extract_pdf.php`'s dispatch to `TemplateExtractor` vs. the AI/text/OCR chain) — extend that check, don't hardcode a new assumption. **No Composer package involved**: this environment has no working `composer`/ext-zip, so `xlsx_writer.php`/`xlsx_reader.php` hand-roll the handful of OOXML XML parts an `.xlsx` needs. **Reading** unzips with `PharData` (works with `phar.readonly = On`, which only restricts executable `.phar`s, not data archives); **writing** (`xlsx_zip_parts()`) builds the zip container itself with `gzdeflate()` — do not switch it back to `PharData`, whose archives (version-needed 0 plus a per-entry extra field) Excel refuses to open even though PHP can read them back. Don't reach for PhpSpreadsheet or `ZipArchive` without first checking those are actually available.

**Bulk update of HGE applications (ADMIN page, `admin/admin_tools.php`)**: files many applications at once from a spreadsheet of applicants (`CoEIssueDate`, `LName`, `FName`, `MI`, `MName`, `ExtName` — the source system's own export columns), as an alternative to filing one graduate at a time from `lookup.php`. It is always **upload → preview (dry run) → confirm**; nothing is written before the admin confirms. `api/bulk_hge_preview.php` reads the file with `bulk_hge_read_upload()` (`includes/bulk_hge.php`: extension *and* magic-byte check, max 10 MB / 50,000 rows, the upload itself is never stored) using `xls_read_first_sheet()` (`includes/xls_reader.php`, a hand-rolled BIFF8/OLE2 reader for legacy `.xls` — it returns date cells as raw Excel serials like the `.xlsx` reader, rejects BIFF5/encrypted files with a "save as .xlsx/.csv" message, and is exercised by `tests/includes/XlsReaderTest.php` against a real Excel-written fixture plus a hand-built OLE2 mini-stream container), `xlsx_read_first_sheet()` or `csv_read_rows()` (`includes/csv_reader.php`: BOM, Windows-1252, `,`/`;`/tab). `parse_bulk_hge_rows()` (pure, DB-free) finds the header row within the first 10 rows (so the downloadable template's instruction block and a raw export both work; aliases such as DATE APPLIED / LAST NAME are accepted), treats `_` (and junk like `__.`) in MI/MName as "no middle name", normalizes ExtName, parses dates (Excel serial, ISO, `m/d/Y`), reports unreadable rows instead of dropping them and merges repeated people keeping the earliest date. Matching against `latin_honor_graduates.graduate_name` is token-based because that column is free text in many shapes (`LAST, FIRST M.`, `First M. Last`, honorifics, stray GWA numbers, `Ñ`): `bulk_hge_candidate_level()` requires every LName/FName token to appear and every leftover token to be explained by the middle name (word or initial). *Confident* matches are filed; *loose* (saved record has no middle name but the file does), *ambiguous* (several different records fit — except exact duplicate copies, which collapse to the keeper using `duplicate_exact_copy_key()`'s strict rule — school, year, honor, name AND course, deliberately NOT the looser name + course key, so two schools' records are never merged into one when filing an application) and *claimed by two people* matches are excluded and kept as **action items**: when the admin confirms the preview they are saved in `bulk_hge_review_items` (one row per person, `person_key`; created by `database/add_bulk_hge_review.sql` on a live DB — there is no migration runner) and listed in a persistent NEEDS REVIEW section on the ADMIN page (`api/bulk_hge_review_list.php`) (a GO TO NEEDS REVIEW (n) button in the card's top row scrolls to it while items wait, and confirming a preview that saved items scrolls there automatically) until the admin files the application against one of the possible saved records (`api/bulk_hge_review_resolve.php`, `action=file` → `bulk_hge_review_file()`, uses the file's date as both `application_date` and `approved_at` — always a fresh INSERT, refused if the graduate already has an application — and logs `application_filed`; a candidate that is already filed but NOT yet approved instead offers APPROVE THIS RECORD, `action=approve` → `bulk_hge_review_approve()`, which sets `approved_at` to the file's date and `approved_by`, keeps the original `application_date`, refuses a record with no application or one already approved, and closes the item as `filed`; the list flags each candidate with `applied_on` and `approved`) or dismisses it (`action=dismiss`; a dismissed or filed person is not raised again by a later upload; an item is closed automatically as soon as ANY of its possible records is already filed AND APPROVED for the file's own date (a filed but not yet approved record keeps the item open so it can be approved) — someone already acted on that applicant, e.g. the same person typed twice with different spellings or a same-named twin on another campus that stays unfiled (a record filed for a different date does not count) — it is closed as dismissed by `bulk_hge_review_close_settled()` when the list loads, and is not saved at all by `bulk_hge_review_save()`; `bulk_hge_review_classify()` gives each uncertain applicant one verdict — `open`, `settled` or `resolved` (already filed/dismissed) — and the preview counts only `open` ones as NEEDS REVIEW and reports the rest as `handled`, so it never offers a review that confirming would not save) — `includes/bulk_hge_review.php`; the preview also offers a downloadable review file (`api/bulk_hge_review_report.php`, from the session) with the uncertain and unreadable rows; the file's date (CoEIssueDate) is the APPROVAL date, not just the filing date — `bulk_hge_insert_pairs()` upserts `graduate_applications`: a graduate with no application is filed AND approved on that date (`application_date` = `approved_at`, `approved_by` = the confirming admin), one filed but still processing is approved with that date (its original `application_date` is kept), and an already-APPROVED graduate is skipped and only counted (`already_approved`); people with no Latin Honor record are only counted (the source list is the whole HGE applicant table, so most rows legitimately are not found). The preview stages the confident `(graduate_id, date)` pairs in `$_SESSION['bulk_hge_preview']` under a one-time token; `api/bulk_hge_apply.php` consumes it (30-minute expiry), files/approves the applications and saves the review items in ONE transaction via `bulk_hge_apply_with_review()` (a graduate filed in the meantime is skipped, never overwritten) and logs one `application_filed` activity entry. `api/download_bulk_hge_template.php` serves the template (`build_bulk_hge_template_xlsx()`). Covered by `BulkHgeParseTest`, `BulkHgeMatchTest`, `BulkHgeApplyTest`, `BulkHgeReviewTest`, `CsvReaderTest` and `XlsReaderTest`.
**`admin/school_records.php` vs. `admin/lookup.php`** cover different sides of the data model: `school_records.php` is upload-centric (lists `latin_honor_uploads` rows, filterable by school/school year, with per-upload aging/status and actions to view, reopen-for-edit, or delete an empty upload — "which uploads exist and what's their review status"), while `lookup.php` is graduate-centric (searches already-saved `latin_honor_graduates` rows by name/school/year — "does this specific person hold a Latin Honor," the public-facing verification use case this whole system exists for). Bulk graduate mutations follow the same split: `api/mass_update_staged_date.php`/`api/delete_graduates.php` touch **staged** review-session rows (pre-save, scoped to one upload); `api/bulk_update_graduation_date.php`/`api/delete_saved_graduate.php`/`api/update_saved_graduate.php` touch **saved** `latin_honor_graduates` rows (post-save — the school+year-scoped bulk date fix and the single-record edit/delete reachable from `lookup.php`/`school_records.php`).

**Duplicates are decided by NAME alone** (`duplicate_group_key()` in `includes/duplicates.php`, after case/spacing/punctuation normalization) — wherever the copies are saved: course, school, graduation year, Latin honor and date are NOT part of the key, because the same person is often on two schools' lists (another campus, a list uploaded under the wrong school), the same course is written many ways ("BSIT" vs "Bachelor of Science in Information Technology") and OCR drops dates and mangles honors. **A record that already has a filed application prevails** over the other copies (the system has no separate "confirmed" state — filing the application is the confirmation): `group_duplicates()` always lists it first as the one to keep, `remove_duplicate_graduates()` never removes it (nor the last remaining copy), and the SAVE RECORDS prompt shows it in green as "THIS RECORD PREVAILS" and pre-ticks the copies in the review for removal. Without an application the oldest copy is the suggested keeper. This one key drives the Look-Up duplicate flag (`flag_duplicates_for_rows()`), `admin/duplicates.php` (`find_duplicate_groups()` — its school/year filters only choose which groups to show; each group still lists every copy with its school, course, honor and year), the post-save "N possible duplicates" count (`count_duplicates_for_upload()`), the cleanup tool and the SAVE RECORDS prompt below. The bulk update of applications keeps its own strict `duplicate_exact_copy_key()` (school, year, honor, name AND course) on purpose, so two schools' records are never merged when filing an application.

**Recycle bin (`admin/recycle_bin.php`)**: nothing removed from the system is destroyed first — it moves to the bin, and every removal is also written to the activity log (`record_removed`, `pdf_delete`, `school_removed`, `user_removed`, `ocr_keyword_removed`; restore = `record_restored`, permanent delete = `record_purged`, so no `activity_log.action` ENUM change was needed). Graduate records use `graduate_recycle_bin` (`archive_graduate()`/`restore_graduate()` in `includes/recycle_bin.php`, covering manual deletes, duplicate cleanup and records removed while re-reviewing saved records). Everything else uses the generic `recycle_bin_items` table (`includes/recycle_bin_items.php`; created by `database/add_recycle_bin_items.sql` on a live DB — there is no migration runner): `archive_item()` stores a JSON snapshot of the removed rows, inside the same transaction as the DELETE, for an **upload** (`delete_upload()` — the row, its saved draft and any attached graduates; its PDF/template file is MOVED into `storage/recycle_bin/`, closed to the web like the other storage folders, and moved back on restore), a **school** (`remove_school()`), a **user** (`remove_user()` — including the ids of the activity-log rows it anonymized, re-attached on restore) and an **OCR keyword** (`remove_ocr_course_keyword()`). `restore_recycle_item()` re-inserts under the ORIGINAL id and refuses with a readable error when it would clash with what exists now (same upload number, school name+campus, username/email, keyword, or an occupied file path); `purge_recycle_item()` deletes for good, binned file included. The page lists both tables through `get_recycle_bin_combined()` (type/name/removed-by filters) and the selection posts `12` for a graduate record and `i12` for a generic item to `api/restore_graduates.php` / `api/purge_recycle_bin.php`. Until the SQL file is run, those removals are refused with a message (nothing is removed) and the page still lists graduate records. Covered by `DuplicatesAndRecycleBinTest` and `RecycleBinItemsTest`.

**Data model** (`database/schema.sql`): `users` → `schools` → `latin_honor_uploads` (one PDF/template, unique per `school_id`+`school_year`+`upload_number`, tracks `extraction_status`: `pending`→`extracted`/`failed`→`reviewed`, or `draft` while a review is saved-but-not-finalized) → `extraction_review_drafts` (one row per `upload_id`, holds the in-progress review as `rows_json` — see the extraction pipeline's step 4) → `latin_honor_graduates` (one row per applicant, FULLTEXT-indexed on `graduate_name`; `source` ENUM `ai`/`ocr`/`text`/`manual` records which extractor produced the row — set by the extractors themselves (`$row['source']`), overwritten to `manual` the moment an admin edits a row in `admin/review.php` (`set_staged_row()`), carried through `save_staged_records()` into the DB, and shown as a small badge on `admin/lookup.php` via `extraction_source_label()`/`extractionSourceLabel()`; `NULL` for anything saved before this was tracked — never backfilled, so an older record simply shows no badge) → `graduate_applications` (records that a searched applicant's Latin Honor was actually filed, via `api/file_application.php`/`includes/graduates.php:file_application()`, one `application_date` per graduate). `activity_log` records auditable actions (`login`, `logout`, `pdf_upload`, `pdf_delete`, `template_upload`, `record_created/updated/removed/restored/purged`, `record_draft_saved`, `search`, `user_created/updated/removed`, `school_created/updated/removed`, `application_filed`, `db_backup`, `ocr_keyword_created/removed`) and self-prunes rows older than 6 months on every write (`log_activity()`).

**Frontend**: server-rendered PHP views (all-caps UI copy throughout — labels, buttons, error messages) styled with Tailwind compiled to a single static `assets/css/app.css` (rebuild with `npm run build:css` after editing `assets/css/input.css` or changing Tailwind classes in PHP — content scanning covers `./**/*.php` and `./assets/js/**/*.js`). Tailwind's `dark:` variant is used throughout for a dark theme, toggled client-side by `assets/js/theme.js` (flips a `dark` class on `<html>`, persisted to `localStorage['hge_theme']` — no server round-trip). Per-page vanilla JS in `assets/js/` (one file per admin page, e.g. `upload.js`, `review.js`, `lookup.js`) talks to the `api/*.php` endpoints via `fetch`, posting `csrf_token` from the page. `includes/header.php`/`sidebar.php`/`footer.php` are shared layout partials included by every `admin/*.php` page; `asset_url()` appends `?v=<filemtime>` so edits bust the browser cache without a build step. **`admin/help.php`** (HELP, open to every signed-in user) is the one deliberate exception to the all-caps copy: the guide is plain data in its `$sections` array (steps, tips, notes and security notices; `[[LABEL]]` marks a real button/field name and is shown highlighted in capitals), rendered in sentence case as one chapter at a time — collapsible contents groups (`$chapterGroups`/`$chapterMeta` give each section its group and icon), Previous/Next, a progress bar, an all-chapters search and a back-to-top button, driven by `assets/js/help.js` (viewed chapters are remembered in `localStorage['hge_help_seen']`; without JavaScript every chapter is shown). Administrator-only sections/parts are left out for a plain user and carry a subtle "Admin only" label; when a button or flow changes, update the text there. Chapters carry screenshots (`$helpFigures` in `admin/help.php`, keyed by chapter id or `chapter-id#part-index`; `help_render_figures()` shows the `-light`/`-dark` WebP pair for the active theme, lazy-loaded, with a click-to-enlarge `<dialog>` in `help.js`) kept in `assets/images/help/`. They were captured from a throw-away database of made-up sample data (never real graduate records) — when a page's look changes noticeably, retake them with `node tools/help-screenshots/capture.mjs [--only name]` (it fills a separate `hge_help_shots` database, serves the app on 127.0.0.1:8099, photographs the pages in headless Chrome and drops the database again — see its README; `login.php` there only answers under `php -S` against that database) and keep the file names.

**Config via environment**: `config/database.php` reads `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASS`/`APP_BASE_URL` via `getenv()`, defaulting to XAMPP-local values (`127.0.0.1` / `hge_masterlist` / `root` / empty / `/hge_masterlist`). It also pins timestamps to the Philippines: `date_default_timezone_set('Asia/Manila')` for PHP's own clock, and every PDO connection sets `SET time_zone = '+08:00'` via `PDO::MYSQL_ATTR_INIT_COMMAND` so MySQL's own `CURRENT_TIMESTAMP` defaults agree with PHP-stamped times (e.g. in `activity_log`) — don't let a new connection path skip that init command. OCR tool paths follow the same `getenv()`-with-Windows-default pattern in `extractors/ocr_extractor.php` and `includes/ocr_tools.php` (`GHOSTSCRIPT_PATH`/`TESSERACT_PATH`); `api/backup_database.php` reads `MYSQLDUMP_PATH` the same way, defaulting to the XAMPP-bundled `mysqldump.exe`; `config/gemini.php` reads `GEMINI_API_KEY`/`GEMINI_API_KEY_2`/`GEMINI_API_KEY_3`/`GEMINI_API_KEY_4`/`GEMINI_MODEL` with no hardcoded key default (see the extraction pipeline above).

**OCR tool bootstrap**: `includes/ocr_tools.php` can check (`check_ocr_tools_installed()`) and silently install Ghostscript/Tesseract when missing, driven from the dashboard via `api/install_ocr_tools.php`. The Ghostscript installer is downloaded from a pinned GitHub release URL and its SHA-256 is verified against a hardcoded constant before running `/S` (silent install); Tesseract is installed via `winget`. Don't change the pinned installer URL/hash without also updating the other.
