# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HGE Database — Honor Graduate Eligibility Latin Honor Database. A plain-PHP (no framework) web app where schools' PDF lists of Latin Honor graduates are uploaded, OCR/text-extracted into structured records, reviewed/corrected by a human, saved, and later searched to verify whether an applicant holds a Latin Honor for a given school/year. The original PDF is always retrievable as the source of truth.

Design spec and phase plans (useful for "why" context, not just "what"): `docs/superpowers/specs/` and `docs/superpowers/plans/`.

Terminology used consistently in code/UI: **HGE**, **Application** (this system), **PDF** (an uploaded school list), **Latin Honor** (`CUM LAUDE` / `MAGNA CUM LAUDE` / `SUMMA CUM LAUDE`), **Applicant** (a graduate holding a Latin Honor — never the uploader).

## Commands

```
composer install                 # PHP deps (smalot/pdfparser, tesseract_ocr, phpunit)
npm install                      # Tailwind
npm run build:css                # compile assets/css/input.css -> assets/css/app.css (minified)

vendor/bin/phpunit                                    # run full test suite
vendor/bin/phpunit tests/includes/FunctionsTest.php   # single file
vendor/bin/phpunit --filter testMethodName            # single test
```

Tests need a real MySQL/MariaDB server reachable at `127.0.0.1` as `root` with no password (`tests/TestDb.php` creates/tears down a separate `hge_masterlist_test2` database from `database/schema.sql` — it does not touch `hge_masterlist`; the name has a `2` because the original `hge_masterlist_test` picked up permanent InnoDB dictionary corruption on one dev machine — see `TestDb::DB_NAME`'s comment — and was abandoned rather than repaired in place). There is no PHP lint/static-analysis command configured. `tests/config/DatabaseTest.php` connects to `hge_masterlist_test2` directly without creating it, so running it in isolation on a machine that has never run the full suite fails with "unknown database" — run the full suite (or any other `TestDb`-using test class) at least once first.

CI (`.github/workflows/tests.yml`) runs the same `vendor/bin/phpunit` against a MySQL 8.0 service container on PHP 8.2, with Ghostscript/Tesseract installed via `apt-get` (paths resolved into `GHOSTSCRIPT_PATH`/`TESSERACT_PATH` env vars) and `npm run build:css` run first — mirror that setup when debugging a CI-only failure.

The app itself is served by XAMPP/Apache at `http://localhost/hge_masterlist/` — there is no dev server to start.

## Architecture

**No framework, no router, no autoloader for app code.** Every page under `admin/*.php` and every endpoint under `api/*.php` is a standalone script that begins by manually `require_once`-ing exactly the `config/` and `includes/*.php` files it needs (order matters: `config/database.php`, then `includes/functions.php`, then `includes/auth.php`, then feature-specific includes). Only `vendor/` (Composer deps and the `Tests\` namespace) is autoloaded. When adding a new admin page or API endpoint, follow the require pattern of a sibling file rather than inventing a bootstrap file.

**`includes/*.php` are function libraries, not classes** (except the extractors). Each file groups plain functions around one concern: `auth.php` (session, CSRF, login, role checks), `functions.php` (view helpers: `e()`/`e_upper()` escaping, `asset_url()` cache-busting via `filemtime`, pagination, flash messages, dashboard stats), `uploads.php`, `schools.php`, `graduates.php`, `users.php`, `activity.php`, `extraction_review.php`, `pdf_files.php`. All DB access takes an explicit `PDO $pdo` parameter — nothing reaches for a global connection inside these functions (call `get_pdo()` once in the page/endpoint and pass it down).

**Auth/session model**: `require_login()` / `require_role('administrator')` (see `includes/auth.php`) gate every admin page and API endpoint. Roles are `administrator` and `user`; `user_has_role()` treats `administrator` as satisfying any role check. Every state-changing API endpoint verifies `csrf_verify($_POST['csrf_token'])` before doing anything else — copy this check when adding a new endpoint. `attempt_login()` deliberately runs `password_verify()` against a fixed dummy bcrypt hash when the user doesn't exist or is disabled, to avoid a timing side-channel; don't "simplify" that away. For especially sensitive actions (e.g. `api/backup_database.php`), a valid session + CSRF token isn't enough: the endpoint re-collects username/password from the request body and re-runs `attempt_login()` fresh ("step-up" re-authentication) before proceeding — follow that pattern for any new endpoint that exports/destroys data at that level of sensitivity. Idle-session timeout is enforced server-side in `require_login()` against `SESSION_IDLE_TIMEOUT` (`config/database.php`, default 14400s/4h, `getenv()`-overridable) and mirrored client-side: `includes/footer.php` emits the same timeout value to `assets/js/idle_timeout.js`, which pings `api/keep_alive.php` on user activity to reset `$_SESSION['last_activity']` before it expires, and otherwise redirects to `login.php?timeout=1`.

**Extraction pipeline** (the core domain logic). PDF is the primary input path:
1. `admin/upload.php` → `api/upload_pdf.php` → `handle_upload_request()` in `includes/uploads.php`: validates the PDF, finds/creates the school, detects duplicate school+school_year uploads (requires `confirm_duplicate` to overwrite), builds a collision-safe stored filename, copies the file into `storage/pdfs/` (denied to direct web access via its `.htaccess`), and inserts a `latin_honor_uploads` row.
2. `api/extract_pdf.php` runs a fallback **chain**, each stage only tried when the previous one fails: **`GeminiExtractor`** (the primary path) sends the PDF's raw bytes directly to the Gemini API (`config/gemini.php`: `GEMINI_API_KEY`/`GEMINI_API_KEY_2`/`GEMINI_API_KEY_3`/`GEMINI_API_KEY_4`/`GEMINI_MODEL` via `getenv()`, no hardcoded default for the keys — an unset key makes it fail immediately and fall through, so a fresh clone works unmodified) and asks it to read the document and return structured JSON rows directly, understanding layout (wrapped cells, borderless columns, narrative certification letters) without a bespoke per-layout handler. It tries each configured key in turn, up to four (a 429 skips straight to the next key — quota exhausted, no point waiting; a 503 or transport failure gets 2 short-backoff retries on the *same* key first), and `extract_pdf.php` gives it one bounded extra whole-extractor retry when the failure wasn't quota/connectivity-related. If AI still fails, **`GenericExtractor`** (text-layer via `smalot/pdfparser`, fast/free, no OCR) is tried next; only if that also yields zero rows does `extract_pdf.php` return `ocr_confirm_required` and wait for the admin to explicitly opt into **`OcrExtractor`** (Ghostscript rasterizes pages to PNG, then `thiagoalessio/tesseract_ocr` OCRs each page — paths configurable via `GHOSTSCRIPT_PATH`/`TESSERACT_PATH` env vars) via `use_ocr=1`, since OCR is the slowest and least accurate option and shouldn't run silently. `GeminiExtractor::isQuotaExhausted()`/`getUsageStats()` back a usage-gauge/notice on `admin/upload.php`, backed by a small JSON cache file in `storage/cache/` (not the DB — disposable, resets daily) rather than a real "remaining quota" figure (the free tier exposes none). All extractors implement `ExtractorInterface::extract()`; `GenericExtractor`/`OcrExtractor` additionally share row-parsing logic via the `ParsesHonorRows` trait (AI output needs no such parsing — Gemini returns the fields directly).
3. `ParsesHonorRows::parseRows()` (used by `GenericExtractor`/`OcrExtractor` only) is line-oriented text parsing (no ML/NLP): it locates the honor phrase (`CUM LAUDE` family) on a line, then works backwards/forwards from that position to pull name, course, GWA, and date, handling name-first, "course-first" (anchored on `BACHELOR`), and "honor-first" (honor between name and course, or leading the line with the row's name/number OCR'd onto a separate fragment) layouts. A line with no honor phrase is tried as a **ditto row** (`parseDittoLine()`) — many Philippine school lists repeat `"- do -"` in the Honor Received/Date columns instead of retyping the same value; since real OCR renders that mark wildly inconsistently ("do", "odo", or unrecognizable noise), it's detected by anchoring on the course keyword instead of the ditto text itself, then `resolveDittoMarks()` backfills honor/date from the nearest earlier row in a second pass over the whole document. Separately, when a table cell's course text wraps onto 2-3 lines, OCR sometimes splits the honor phrase itself across the line break — `mergeSplitHonorLines()` (run before per-line parsing) joins such a line with the next one whenever that completes a recognizable honor phrase within the next line's first ~20 characters. `mergeOrphanedHonorFragmentLines()` similarly re-attaches an honor tier name OCR'd onto its own line, separated from the row's actual content by a genuinely blank line. `matchHonor()`'s CUM↔LAUDE gap is intentionally bounded slop (not `\s*`) to tolerate what typically sits in that gap once merged. Whichever extractor produced them, rows are staged into `$_SESSION['extraction_review']` (see `includes/extraction_review.php`), never written to `latin_honor_graduates` directly.
4. `admin/review.php` lets a human edit staged rows (`set_staged_row()`), remove one (`remove_staged_row()`) or several at once (`remove_staged_rows()`, multi-select bulk-delete UI), and mass-set a graduation date across every staged row (`mass_update_staged_graduation_date()`, for lists whose PDF never had a date column). Every removal path — staged (`api/delete_graduate.php`/`api/delete_graduates.php`) and already-saved (`api/delete_saved_graduate.php`) — requires a free-text `reason` first (`validate_removal_reason()` in `includes/functions.php`: non-empty, letters/numbers only, rejects placeholders like "N/A" or "-"), folded into the `record_removed` activity-log entry rather than stored on the row itself. A review in progress can also be persisted server-side rather than only living in `$_SESSION`: `api/save_draft.php` → `save_extraction_draft()` writes the staged rows into `extraction_review_drafts` (one row per `upload_id`) and sets `extraction_status` to `draft`, so it survives past the session and can be resumed later. `api/save_records.php` → `save_staged_records()` validates every row (`validate_staged_row()`) and, in one transaction, reconciles them against the DB by `id`: rows carrying an `id` (seeded by `get_graduates_for_upload()` when **reopening an already-`reviewed` upload for editing**, e.g. from `admin/school_records.php`'s "Edit saved records" link) are UPDATEd in place, rows without one are INSERTed as new, and any existing saved row whose `id` no longer appears in the submitted set is DELETEd — so the same function handles a first-time save and a later correction to already-saved records alike, only then setting `extraction_status` to `reviewed`.

When changing text-based parsing behavior, extend `ParsesHonorRows` (shared by `GenericExtractor`/`OcrExtractor`) rather than duplicating logic in one extractor, and check `tests/extractors/GenericExtractorTest.php` / `OcrExtractorTest.php` plus the PDF/OCR-output fixtures in `tests/fixtures/` (including `course-first-sample.pdf`, `course-first-scanned.pdf`, `ditto-sample-ocr-output.txt` — verbatim real Tesseract output of a ditto-mark honor list, `wrapped-course-honor-split-ocr-output.txt` — verbatim real Tesseract output of a wrapped-course honor list, `bped-bsab-course-ocr-output.txt` — verbatim real Tesseract output covering the `BPED`/`BSAB` course abbreviations, `vsu-honor-first-ocr-output.txt` — a layout where the honor sits between name and course, and `sti-ormoc-honor-leading-ocr-output.txt` — a layout where the honor tier is OCR'd onto its own orphaned line ahead of the row it belongs to, all used as-is rather than re-OCR'd on every test run) for the layouts already covered. `tests/extractors/GeminiExtractorTest.php` covers `GeminiExtractor` against a stubbed API base URL (`buildGeminiRequestPayload()`/`parseGeminiResponseRows()` are pure and unit-tested directly; transport failures are exercised by pointing `$apiBaseUrl` at an unreachable local address, no real network dependency). The hardcoded `COURSE_KEYWORDS` list (only relevant to the text-parsing fallback path) is not exhaustive — when a GenericExtractor/OcrExtractor document has a row that silently disappears, it's almost always a missing course abbreviation there. Rather than editing code for a one-off addition, an administrator can add it live via **Settings → OCR Course Keywords** (`admin/ocr_courses.php`): `includes/ocr_keywords.php` stores admin-added keywords (always uppercased, restricted to `A-Z0-9.- ` to keep every row a plausible abbreviation) in the `ocr_course_keywords` table, `api/extract_pdf.php` loads them and passes them into `new GenericExtractor($keywords)` / `new OcrExtractor($keywords)`, and `ParsesHonorRows::courseKeywordPattern()` compiles them (`preg_quote()`'d — never trusted as a regex fragment) alongside the hardcoded list into the same pattern used everywhere `COURSE_KEYWORD_PATTERN` used to be referenced directly.

**Upload From Template (Excel), an alternate input path**: alongside PDF, `admin/upload.php`'s "EXCEL TEMPLATE" tab lets an admin skip extraction entirely by filling in a structured `.xlsx` template instead. **Download**: `api/download_template.php` (`?school_id=`) generates it on the fly via `build_latin_honor_template_xlsx()` in `includes/xlsx_writer.php`, pre-filling the exact `school_name`/`campus` from the DB so a re-upload always matches. **Upload**: `api/upload_template.php` → `handle_template_upload_request()` in `includes/template_upload.php` does in one request what the PDF path spreads across two (`upload_pdf.php` + `extract_pdf.php`), since there's no extraction step: read the file (`xlsx_read_first_sheet()` in `includes/xlsx_reader.php`), validate its header block + column layout (`parse_latin_honor_template()` — pure/DB-independent, unit-tested in `tests/includes/TemplateParsingTest.php` without a DB), resolve the school via `find_school_by_exact_name_campus()` (unlike the PDF form, **never** auto-creates a school — an unrecognized school is a hard `school_not_found` error telling the admin to add it in School Management first), then the usual duplicate-check/store/`create_upload_record()`/`start_extraction_review()` sequence — it lands in the same `$_SESSION['extraction_review']` staging session as the PDF path, so review/save downstream is shared. The `.xlsx` itself is kept as the source-of-truth file in `storage/templates/` (sibling to `storage/pdfs/`, same `.htaccess` deny), and `TemplateExtractor` (in `extractors/`, implements `ExtractorInterface` like the others, covered by `tests/extractors/TemplateExtractorTest.php`) re-runs the same reader/parser pair for RE-EXTRACT RECORDS. Since a `latin_honor_uploads` row's stored file can now be either format, anything that assumed "PDF" checks `pathinfo($upload['stored_filename'], PATHINFO_EXTENSION)` instead (`admin/view_upload.php`'s FILE FORMAT/quick actions, `admin/review.php`'s preview button, `api/serve_pdf.php`'s `Content-Type`, `api/extract_pdf.php`'s dispatch to `TemplateExtractor` vs. the AI/text/OCR chain) — extend that check, don't hardcode a new assumption. **No Composer package involved**: this environment has no working `composer`/ext-zip, so `xlsx_writer.php`/`xlsx_reader.php` hand-roll the handful of OOXML XML parts an `.xlsx` needs and zip/unzip them with `PharData` (works with `phar.readonly = On`, which only restricts executable `.phar`s, not data archives) — don't reach for PhpSpreadsheet or `ZipArchive` without first checking those are actually available.

**`admin/school_records.php` vs. `admin/lookup.php`** cover different sides of the data model: `school_records.php` is upload-centric (lists `latin_honor_uploads` rows, filterable by school/school year, with per-upload aging/status and actions to view, reopen-for-edit, or delete an empty upload — "which uploads exist and what's their review status"), while `lookup.php` is graduate-centric (searches already-saved `latin_honor_graduates` rows by name/school/year — "does this specific person hold a Latin Honor," the public-facing verification use case this whole system exists for). Bulk graduate mutations follow the same split: `api/mass_update_staged_date.php`/`api/delete_graduates.php` touch **staged** review-session rows (pre-save, scoped to one upload); `api/bulk_update_graduation_date.php`/`api/delete_saved_graduate.php`/`api/update_saved_graduate.php` touch **saved** `latin_honor_graduates` rows (post-save — the school+year-scoped bulk date fix and the single-record edit/delete reachable from `lookup.php`/`school_records.php`).

**Data model** (`database/schema.sql`): `users` → `schools` → `latin_honor_uploads` (one PDF/template, unique per `school_id`+`school_year`+`upload_number`, tracks `extraction_status`: `pending`→`extracted`/`failed`→`reviewed`, or `draft` while a review is saved-but-not-finalized) → `extraction_review_drafts` (one row per `upload_id`, holds the in-progress review as `rows_json` — see the extraction pipeline's step 4) → `latin_honor_graduates` (one row per applicant, FULLTEXT-indexed on `graduate_name`; `source` ENUM `ai`/`ocr`/`text`/`manual` records which extractor produced the row — set by the extractors themselves (`$row['source']`), overwritten to `manual` the moment an admin edits a row in `admin/review.php` (`set_staged_row()`), carried through `save_staged_records()` into the DB, and shown as a small badge on `admin/lookup.php` via `extraction_source_label()`/`extractionSourceLabel()`; `NULL` for anything saved before this was tracked — never backfilled, so an older record simply shows no badge) → `graduate_applications` (records that a searched applicant's Latin Honor was actually filed, via `api/file_application.php`/`includes/graduates.php:file_application()`, one `application_date` per graduate). `activity_log` records auditable actions (`login`, `logout`, `pdf_upload`, `pdf_delete`, `template_upload`, `record_created/updated/removed`, `record_draft_saved`, `search`, `user_created/updated/removed`, `school_created/updated/removed`, `application_filed`, `db_backup`, `ocr_keyword_created/removed`) and self-prunes rows older than 6 months on every write (`log_activity()`).

**Frontend**: server-rendered PHP views (all-caps UI copy throughout — labels, buttons, error messages) styled with Tailwind compiled to a single static `assets/css/app.css` (rebuild with `npm run build:css` after editing `assets/css/input.css` or changing Tailwind classes in PHP — content scanning covers `./**/*.php` and `./assets/js/**/*.js`). Tailwind's `dark:` variant is used throughout for a dark theme, toggled client-side by `assets/js/theme.js` (flips a `dark` class on `<html>`, persisted to `localStorage['hge_theme']` — no server round-trip). Per-page vanilla JS in `assets/js/` (one file per admin page, e.g. `upload.js`, `review.js`, `lookup.js`) talks to the `api/*.php` endpoints via `fetch`, posting `csrf_token` from the page. `includes/header.php`/`sidebar.php`/`footer.php` are shared layout partials included by every `admin/*.php` page; `asset_url()` appends `?v=<filemtime>` so edits bust the browser cache without a build step.

**Config via environment**: `config/database.php` reads `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASS`/`APP_BASE_URL` via `getenv()`, defaulting to XAMPP-local values (`127.0.0.1` / `hge_masterlist` / `root` / empty / `/hge_masterlist`). It also pins timestamps to the Philippines: `date_default_timezone_set('Asia/Manila')` for PHP's own clock, and every PDO connection sets `SET time_zone = '+08:00'` via `PDO::MYSQL_ATTR_INIT_COMMAND` so MySQL's own `CURRENT_TIMESTAMP` defaults agree with PHP-stamped times (e.g. in `activity_log`) — don't let a new connection path skip that init command. OCR tool paths follow the same `getenv()`-with-Windows-default pattern in `extractors/ocr_extractor.php` and `includes/ocr_tools.php` (`GHOSTSCRIPT_PATH`/`TESSERACT_PATH`); `api/backup_database.php` reads `MYSQLDUMP_PATH` the same way, defaulting to the XAMPP-bundled `mysqldump.exe`; `config/gemini.php` reads `GEMINI_API_KEY`/`GEMINI_API_KEY_2`/`GEMINI_API_KEY_3`/`GEMINI_API_KEY_4`/`GEMINI_MODEL` with no hardcoded key default (see the extraction pipeline above).

**OCR tool bootstrap**: `includes/ocr_tools.php` can check (`check_ocr_tools_installed()`) and silently install Ghostscript/Tesseract when missing, driven from the dashboard via `api/install_ocr_tools.php`. The Ghostscript installer is downloaded from a pinned GitHub release URL and its SHA-256 is verified against a hardcoded constant before running `/S` (silent install); Tesseract is installed via `winget`. Don't change the pinned installer URL/hash without also updating the other.
